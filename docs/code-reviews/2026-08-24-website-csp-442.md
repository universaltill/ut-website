# 2026-08-24 — ut-docs#442: Content-Security-Policy for staticwebapp.config.json

**Card:** [ut-docs#442](https://github.com/universaltill/ut-docs/issues/442)
**Complexity:** medium — **Build model:** Sonnet (inline) — **Review model:** Opus, independent worktree-isolated subagent

## Scope correction found during grooming

The original ticket assumed a CSP was needed mainly to protect `/admin`
(Decap CMS, holding a GitHub token in `localStorage`) on this Static Web
App, and warned that a naive policy risked silently breaking `/admin`'s
pinned-SRI `unpkg.com` script, its ~90 dynamically loaded chunks, and the
Zitadel OIDC redirect.

That premise is stale. `/admin` and its GitHub OAuth relay (`api/auth`,
`api/callback`) were removed from this repo entirely in ut-docs#471/#468
and now live on a separate homelab-cluster-hosted service
(`admin.universaltill.com`, gated by oauth2-proxy/Zitadel with its own
tests) — confirmed via `scripts/check-swa-config.js` (CI-enforced: fails
if `/admin`, `api/`, or `site/admin/` ever reappear here) and a repo-wide
grep finding zero references. This repo today is a pure static
marketing/blog/plugins site with **zero external/third-party resources**
anywhere: every `<script src>`, `<link rel=stylesheet>`, image and icon is
same-origin. The one cross-origin call in the whole site is
`download.html`'s client-side `fetch("https://api.github.com/...")` that
upgrades the download links to the live GitHub release.

The CSP was still built — real defense-in-depth (XSS protection) for the
marketing/blog/plugins pages remains worthwhile even without `/admin` in
the threat picture — but scoped to what this site actually loads, which
turned out much simpler than the original ticket anticipated.

## What shipped

- `site/staticwebapp.config.json`'s `globalHeaders` carries a CSP:
  `default-src 'none'`; `script-src 'self'` plus SHA-256 hashes of the
  site's executable inline `<script>` bodies; `style-src 'self'
  'unsafe-inline'` (documented exception — dozens of one-off `style="…"`
  layout attributes, materially lower risk than `unsafe-inline` on
  `script-src`); `img-src 'self' data:` (the CSS icon masks);
  `font-src 'self'`; `connect-src 'self' https://api.github.com`
  (`download.html`'s live-release fetch); `object-src 'none'`;
  `base-uri 'self'`; `form-action 'self'`; `frame-ancestors 'none'`.
- New `scripts/generate-csp.js` (`--check`/`--write`, mirrors
  `check-i18n-keys.js`'s convention) computes the `script-src` hash list
  from a real `dist/` build rather than a hand-written value, so it can't
  drift from what the site actually ships.
- `scripts/serve-site.js` (Playwright's test server) now applies
  `globalHeaders` to every response, not just `routes` — needed so
  `tests/csp.spec.js` can verify the CSP against a real browser rather
  than a hand-approximation.
- New `tests/csp.spec.js`: real Chromium, asserts the header is present
  and asserts **zero** `securitypolicyviolation` events across every
  page shape the site serves (derived from `staticwebapp.config.json`'s
  route table and the blog content directory, same convention
  `seo.spec.js` documents).
- CI: `generate-csp.js --check` folded into the existing `build` job
  (not a separate job — needs the same `npm ci && npm run build` that job
  already runs).
- README updated to describe the mechanism.

## Independent review (Opus, worktree-isolated)

Full transcript available on request; summarized here. Ran every local
gate itself (all green, pasted real output, not summarized), verified the
"zero external resources" premise independently (confirmed), verified
`plugins.astro`'s `raw.githubusercontent.com` fetch is build-time-only, not
client-side (confirmed by reading the actual code), and swept **all 25
built pages across all 5 locales** through a real browser — zero CSP
violations, and specifically proved `connect-src` is actually enforced
(a control fetch to `example.com` was blocked and reported; the real
`api.github.com` fetch was allowed through).

**MAJOR finding, fixed:** the first draft's `script-src` hash list also
hashed each blog post's `<script type="application/ld+json">` block, on
the mistaken premise that CSP governs it the same way it governs the
site's executable scripts. It doesn't — `script-src` only ever applies to
a `<script>` whose type is empty, a JS MIME type, `module`, or
`importmap`; a JSON-LD data block's type falls outside that set entirely,
so the browser never subjects it to `script-src` at all. The reviewer
proved this empirically in the pre-installed Chromium (isolated
reproduction, plus a full-site sweep with the JSON-LD hashes removed:
zero violations) and by literally deleting the fix and confirming the test
named for exactly this case still passed — proof the test had no teeth
against the mistake it claimed to guard. Fixed:
- `scripts/generate-csp.js`'s `findInlineScriptHashes()` now filters by
  script `type` and only hashes executable types — the hash list dropped
  from 13 entries to 3 (the www-canonicalization redirect,
  `download.html`'s asset-detect script, `language.html`'s locale
  switcher), and stays exactly 3 regardless of how many blog posts get
  published or translated, closing the "publish a post, CI goes red for
  no reason" cost the first draft would have imposed on every future
  post.
- File header, README, and the CI job comment corrected to state the real
  browser behavior, not the mistaken one.
- `tests/csp.spec.js` rewritten: the vacuous "JSON-LD is not blocked by
  script-src" test (which the reviewer proved would pass even with the
  bug present) replaced with one that specifically pins the fix — a blog
  post's un-hashed JSON-LD causing zero `script-src` violations — plus a
  full page-list derived from `staticwebapp.config.json`'s routes and the
  blog content directory (previously a hand-copied, en-gb-only list),
  swept across all 5 locales for the header-presence checks and across
  every distinct page *shape* (plain HTML, blog index, blog post,
  `/plugins`) for the violation checks.

Five MINOR findings, all fixed: a test title that didn't match what it
tested (fixed by the page-list rewrite above); a hardcoded page list
against this repo's own documented "derive from source, don't hand-copy"
test convention (same rewrite); a broken Markdown code span split across a
newline in the README; a stale "~20" count of inline `style=` attributes
in a code comment (corrected to describe the actual current count
without hardcoding a number that will go stale again); a dangling
`docs/code-reviews/` reference to this very file (resolved by this file
existing). One NIT (a `\b`-boundary regex quirk that could have matched a
hypothetical `data-src=`/`x-src=` attribute — none exist today, tightened
anyway) also fixed.

**Verdict after fixes: safe to merge.**
